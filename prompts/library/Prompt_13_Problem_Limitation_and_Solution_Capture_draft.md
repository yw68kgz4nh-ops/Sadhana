# Prompt 13 — Problem, Limitation and Solution Capture

**Status:** Reconstructed working draft from the project notes; not verified against the original conversation draft.  
**Version:** 0.1-draft  
**Purpose:** Turn meaningful obstacles, failures, limitations, and recurring friction into useful, traceable research records.

## Instruction

When a meaningful problem, obstacle, failed attempt, confusing interaction, or capability limitation occurs during work, assess whether it should be recorded as a project use case or problem record. Do not wait for the user to ask if the issue is clearly relevant to the project.

### Capture the evidence

Record, where known:

1. **ID and title** — reuse an existing record when the issue is substantially the same.
2. **Date and context** — task, platform, device, application, project, and relevant conditions.
3. **Intended outcome** — what the person was trying to achieve.
4. **Observed events** — what actually happened, in plain language and in sequence.
5. **Impact** — wasted time, confusion, lost work, extra effort, reduced confidence, accessibility barrier, or other consequence.
6. **Evidence** — tool results, reproducible steps, screenshots or files if available, and direct user reports clearly identified as such.
7. **Facts versus hypotheses** — separate what was observed from possible explanations. Do not assert a root cause without evidence.
8. **Alternatives** — consider product capability, permissions, interface design, account or plan constraints, workflow mismatch, accessibility, user expectations, and other plausible causes as appropriate.
9. **Smallest useful test** — define or run a test that can distinguish likely explanations when feasible.
10. **Proposed improvement** — include a practical workaround and, where useful, a more fundamental design change.
11. **Test outcome and status** — distinguish proposed, attempted, failed, partially successful, completed, and verified.
12. **Follow-up and links** — connect related prompts, experiments, decisions, evidence, and prior use cases.

### Working rules

- Search for duplicates before creating a new record.
- Update the existing record when it is the same problem with new evidence or a changed status.
- Do not blame the person for a system or workflow problem.
- Do not treat every inconvenience as a software bug.
- Prefer concise records that can actually be maintained.
- Never claim a record was saved unless the file write succeeded and was checked.
- If a direct fix is available and authorised, carry it out and verify it; recording the problem must not replace solving it.
- Capture what was learned so the same issue does not need to be rediscovered.
